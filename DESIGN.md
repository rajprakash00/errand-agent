# Design — Errand Agent

The model proposes. The kernel disposes. Everything here follows from that
split: a deterministic dialogue machine owns each run, a scripted (or optional)
model only extracts text and drafts replies, and one execution guard is the
sole path to `book`, `cancel`, and `reschedule`.

## The boundary

The public seam is `Conversation.start_run` / `send_message`. The CLI, the
browser, and the eval harness all call it, so a behavior proved in a test is the
behavior a user gets. The model's tool surface is read-only:
`search_providers`, `get_provider`, `list_bookings`, `propose_booking`,
`propose_cancel`, and `propose_reschedule`. Review text is sanitised, labelled
untrusted, and shown as a quote; it never enters the policy path. Even a model
that obeys a prompt injection cannot reach an irreversible primitive.

The stack is Python 3.12, FastAPI/Jinja/HTMX, SQLite in WAL mode, and an
in-process mock provider world. The mock is a contract, not a convenience: it
owns holds and their ten-minute expiry, quote changes, the 70/15/15 booking
outcome mix, timeout-after-commit, the transient cancel 503, and configured
reschedule conflicts. A per-scenario fault plan makes every graded case
reproducible. No network call, API key, or live model is required.

## Approval kernel

A proposal is an immutable snapshot of one intended action: `user_id`, `action`,
`booking_id`, `provider_id`, `slot_start`, `slot_end`, `quoted_price_inr`,
`quote_version`, `hold_id`, and `expires_at`. Its binding hash is
`SHA-256(canonical_json(fields))`.

`book`, `cancel`, and `reschedule` are callable only by `ExecutionGuard`.
Before an irreversible call the guard:

1. reloads the proposal and approval;
2. recomputes the binding hash;
3. requires an unconsumed recorded approval and an unexpired proposal;
4. compares the approved fields with the provider's live hold, voiding the
   approval if the provider, slot, price, quote version, or expiry changed;
5. writes the intent and consumes the approval in one SQLite transaction;
6. calls the primitive, then verifies the provider's status.

The one-transaction claim is the crux. A repeated "yes" finds the consumed
approval and returns the existing booking instead of writing a second intent.
The model cannot write an approval record, set a price, choose a user, or pass
different arguments to a primitive.

## Unknown is not failed

The provider may commit a booking and then time out. The guard treats that as
`unknown`, never as a failure. It calls `get_booking_status` with the same
idempotency key (derived from proposal ID and action) and adopts `booked` only
after `list_bookings` also shows the booking. It retries `book` once with the
same key only when the status says `not_found`. Every attempt, status check, and
reconciliation is a trace event.

The intent row is written before the call. On startup, in-flight and unknown
intents are reconciled from the provider's status before anything else; a
recovery retry reuses the original key. That is why a process death after the
write cannot produce a second booking.

## Dialogue, memory, and exits

The dialogue machine fills only the missing required slot, merges corrections,
and parses a small set of explicit confirmations. Buttons and typed `yes` call
the same approval function. Memory is keyed by user, not run: a stated fact is
active; a hedged model suggestion is inferred and `pending_confirmation`; a
search ignores it until confirmed; a correction archives the old value; forget
deletes the value and writes a tombstone that a replayed chat cannot undo.
Budgets (12 turns, 30 tools, 15 minutes, 90 seconds per turn) are persisted and
checked before each step. Exhaustion ends at `limit_reached`; unexpected errors
end at `failed`; both state that no booking was made and name the trace.

## Evidence

Every run writes an append-only JSONL trace (`seq`, `ts`, `run_id`, `type`,
`payload`, `latency_ms`) and an indexed copy in SQLite. Model calls record a
prompt hash, tool names, tokens, cost, and a short sanitised excerpt; tool calls
record sanitised arguments, results, errors, attempt, and latency. The browser
streams the same events beside the chat and can download the raw file.

The eval harness uses the same seam: 20 scenarios with a fresh temporary
database, a fixed clock, a scripted user, the scripted model, and a
deterministic fault plan. It asserts outcomes, records, tool calls, and trace
events, never reply wording, and checks six global invariants across every
scenario. `EVALS.md` is generated by the run; CI fails if it drifts.

## What breaks first at 100× and what I would change

The first wall is not the model; it is the single-process SQLite writer. At
roughly 100× the current traffic, every claim (approval consumption plus intent
write) serialises on one write lock, and each browser request blocks on
provider latency. I would move the store to Postgres, keep a unique constraint
on the proposal/action pair and the idempotency key, and put provider calls
behind a queue with leases so a run is a resumable state machine rather than a
request.

The second wall is the in-process provider world. Holds, quote versions, and
idempotency must become a real gateway with the same contract, TTLs, and
reconciliation; a mock cannot be shared across workers. The third is evidence
volume: per-run JSONL files and full indexed payloads become an observability
cost. I would stream events to an append-only store with retention, sampling,
and field-level redaction, keeping the event schema so replay and audit still
work.

Approval UX is the subtle one. At 100×, users will approve on multiple devices
and retry across networks; the one-time record still holds, but the UI needs
signed approval tokens, idempotent decision handling, and a visible "already
approved" state. Evals would shift from 20 in-process scenarios to contract
tests against a recorded provider, property tests for exactly-once claims, and
a small live smoke suite. The invariant stays the same: the kernel, not the
model, is the only thing that can spend an approval.
